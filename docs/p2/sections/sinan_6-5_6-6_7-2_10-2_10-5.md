## 6.5 From analysis to architecture

| Analysis object (from 5.1 and 5.2) | Component that owns it (6.3) | Note (split, merged, external) |
|---|---|---|
| Event | C2 Event Storage | C1 creates and merges events. C3 and C4 only read them. |
| Tag | C2 Event Storage | Stored with the event. C1 assigns tags and C3 offers them as filters. |
| Organizer | C2 Event Storage | Stored with the event. C1 reads it from the source page. |
| SourceListing | C2 Event Storage | Saved with the event. C3 links to it. |
| SourceSite | C2 Event Storage | Split. The real sites (R1 UTD Calendar, R2 Nebula Labs) are external and we only read them. C2 keeps our record of each site: address, last checked time and last successful update time. |
| SharedLink | C3 Website | The link is created and opened in the website. |
| EventBrowser (interaction object) | C3 Website | Runs the user's visit and is in control. C3 is the only component the user talks to. |
| EventCatalog (interaction object) | C2 Event Storage | Merged with the stored Events and Tags. It is read access to C2, not a separate component. |
| LinkRegistry (interaction object) | C3 Website | Merged with SharedLink. |

C1 Event Collector owns no analysis object because it is the process that fills C2.
C4 Calendar Download owns none because it builds a file from an Event that C2 owns.

## 6.6 Design principles applied

| Principle | Where it shows in your design | Evidence (component, interface, ADR) |
|---|---|---|
| Separation of concerns | Collecting events, storing them, showing them and making a calendar file are four separate jobs. | C1 Event Collector, C2 Event Storage, C3 Website, C4 Calendar Download |
| Information hiding | Only the collector knows how the UTD Calendar and Nebula pages are laid out. The website never reads a source site and only sees stored events. | 6.3: only C1 connects to R1 and R2. 6.4: the website reads the deployed events.json only |
| Low coupling | The collector and the website share one file, events.json, and never call each other. If a source site changes, only C1 changes. | GitHub Actions writes events.json to the repository and Vercel redeploys. ADR-01 |
| High cohesion | Each component does one thing. C4 only turns one chosen event into an .ics file. C3 only displays and filters events. | 6.3: C4 takes the chosen event and returns an .ics file |
| Design for change | A third event source would be a new reader inside C1, with nothing else changing. The refresh interval and the host are recorded decisions, so they can be swapped. | 6.3: C1 is the only component tied to a source. ADR-02, ADR-03 |
| Keep it simple (KISS) | No accounts, no database server and no user-created events. One scheduled job, one JSON file and a static website on a free plan. | 6.4: Vercel and GitHub Actions only. 1.2: out of scope list |

## 7.2 Trade-off summary

Only the row for ADR-03 is written. The rows for ADR-01 and ADR-02 follow once those
records are final.

| Quality favored | Architectural move | Cost accepted | Recorded in |
|---|---|---|---|
| Low cost (CON-04) and fast page load (QR-01) | Host the website on Vercel, connected to the Git repository. The main branch is the live site and the preproduction branch is the preview site. | The free Vercel Hobby plan limits scheduled jobs, so it may not run the scraper every hour or two. | ADR-03 |
